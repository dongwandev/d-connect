## 컨텍스트

ADR-0001(기술 스택)·ADR-0002(LLM Provider)에서 **무엇을 쓸지**는 정했으나, 그 위에서 **어떻게 코드를 조직할지**는 미결정이었다.

본 ADR은 2026-05-27 회의에서 결정한 10개 항목을 정리한다. 결정에 영향을 미친 컨텍스트:

- **3주 개발 일정** (2026-05-28 ~ 06-17) — 보일러플레이트 최소화 필요
- **2~5명 소규모 팀** — 표준 패턴, 친숙한 컨벤션 우선
- **발표 시연 안정성** — AI 호출 실패에도 흐름 유지 (mock fallback)
- **MVP 도메인 규모** — 엔티티 6종, 사용자 화면 ~5개 페이지
- **AI 코딩 도구 활용** — Claude Code/Codex가 컨벤션을 빠르게 학습할 수 있는 구조

## 결정

### 결정 매트릭스

| # | 항목                  | 채택                                                          |
|---|-----------------------|---------------------------------------------------------------|
| 1 | 레이어 구조           | **3-layer** — Page → Route Handler → DB/AI 직접 호출         |
| 2 | 폴더 구조             | **기능 분리** — `app/` · `server/` · `lib/` · `components/`  |

| 4 | Prisma Client         | **글로벌 싱글톤** — `src/server/db.ts`                       |
| 5 | 에러 처리             | **throw + Route Handler catch + JSON envelope**              |
| 6 | Server / Client 경계  | **기본 server, 인터랙션 leaf만 client**                       |
| 7 | 환경 변수             | **zod 검증 + `env` 객체 export** (`src/server/env.ts`)       |

| 9 | Validation 위치       | **Route Handler 진입 시** (zod parse)                         |
| 10 | 로깅                  | **`console.log` / `console.error`** (MVP)                    |

## 대안 (각 항목별 검토 결과)

### 1. 레이어 구조

| 후보            | 채택 | 사유                                                                |
|-----------------|------|---------------------------------------------------------------------|
| **3-layer**     | ✅    | 엔티티 6종 규모에 Service/Repository는 과한 보일러플레이트          |
| 4-layer         | ❌    | 테스트·교체 용이성 ↑이나 3주 일정엔 부담. 필요 시 점진 도입 가능    |

### 2. 폴더 구조

| 후보              | 채택 | 사유                                                              |
|-------------------|------|-------------------------------------------------------------------|
| **기능 분리**     | ✅    | Next.js 컨벤션과 정합, 친숙도 ↑                                   |
| 도메인 분리       | ❌    | 코드 규모가 커지면 유리하지만 초기엔 오버                          |

### 3. AI 모듈 배치

| 후보                | 채택 | 사유                                                            |
|---------------------|------|-----------------------------------------------------------------|
| **책임별 분리**     | ✅    | mock/실 호출 교체, 프롬프트 재사용, 테스트 용이                 |
| 단일 파일           | ❌    | 기능이 4가지(SDGs 분석 + 콘텐츠 4종)라 단일 파일이 곧 커짐       |

### 4. Prisma Client 인스턴스화

| 후보              | 채택 | 사유                                                              |
|-------------------|------|-------------------------------------------------------------------|
| **글로벌 싱글톤** | ✅    | Next.js dev HMR로 인한 connection leak 방지의 표준 패턴           |
| 매번 new          | ❌    | dev 환경에서 connection pool 폭발                                 |

### 5. 에러 처리

| 후보                | 채택 | 사유                                                            |
|---------------------|------|-----------------------------------------------------------------|
| **throw + Route catch + envelope** | ✅ | JS 표준, 보일러플레이트 적음, Route Handler wrapper 한 번이면 끝 |
| Result 패턴 (`{ ok, data\|error }`) | ❌ | 명시적이지만 모든 함수 시그니처가 무거워짐                       |

### 6. Server / Client 경계

| 원칙                                | 채택 | 사유                                                          |
|-------------------------------------|------|---------------------------------------------------------------|
| **기본 server, 인터랙션 leaf만 client** | ✅ | App Router 베스트 프랙티스. 번들 크기 ↓, 데이터 접근 단순화   |
| 모든 페이지 client                   | ❌    | App Router 이점 상실                                          |

### 7. 환경 변수

| 후보              | 채택 | 사유                                                              |
|-------------------|------|-------------------------------------------------------------------|
| **zod 검증 + env export** | ✅ | startup에서 누락/오타 즉시 검출, 코드 자동완성                  |
| `process.env.X` 직접 사용 | ❌ | 타입 안전성 X, 누락이 런타임에야 드러남                          |

### 8. AI 응답 방식

| 후보            | 채택 | 사유                                                              |
|-----------------|------|-------------------------------------------------------------------|
| **동기**        | ✅    | 단순. 30초 타임아웃 + mock fallback으로 UX 보장                  |
| 비동기 + 폴링   | ❌    | 인프라 복잡도 ↑ (큐, ID 추적, 폴링 핸들러)                       |
| 스트리밍 (SSE)  | ❌    | 콘텐츠 생성에는 좋지만 MVP 범위 초과. 필요 시 콘텐츠 생성만 부분 전환 가능 |

### 9. Validation 위치

| 후보                  | 채택 | 사유                                                          |
|-----------------------|------|---------------------------------------------------------------|
| **Route Handler 진입 시** | ✅ | 비즈니스 로직이 잘못된 입력에 닿지 않음을 보장               |
| Service 레이어        | ❌    | Service 자체가 없음 (#1 결정). 향후 도입 시 재검토            |

### 10. 로깅

| 후보              | 채택 | 사유                                                              |
|-------------------|------|-------------------------------------------------------------------|

## 결과 및 트레이드오프

### 긍정 효과

- **빠른 개발 진입** — Service/Repository 보일러플레이트 없음, Page에서 DB 직접 호출.
- **AI 호출 일관성** — `analyzeSdg()` / `generateContent()` 단일 진입점에서 mock·실 호출 모두 처리.
- **타입 안전성** — env 객체, zod 응답 스키마, Prisma 타입이 컴파일 타임 안전망 형성.
- **시연 안정성** — 4가지 mock fallback 조건(키 부재 / 호출 실패 / 타임아웃 / 스키마 실패) 모두 동일 응답 반환.
- **AI 코딩 도구 친화** — 표준 Next.js 컨벤션을 따라 Claude Code/Codex가 패턴을 빠르게 익힘.

### 부정 효과 / 위험

| 위험                                                | 영향도 | 완화                                                             |
|-----------------------------------------------------|--------|------------------------------------------------------------------|
| Service 부재 → Route Handler가 비대해질 수 있음     | 중     | 1개 Route당 한 가지 일만. 반복 로직이 보이면 그때 Service 도입   |
| 동기 AI 호출 → 사용자가 30초 기다릴 수 있음          | 중     | 로딩 UI + mock fallback 즉시 표시 + 콘텐츠 생성은 향후 스트리밍 검토 |
| Route Handler에서 catch만 → trace 분실 가능성        | 낮음   | `console.error`로 stack 출력. 운영 단계에서 구조화 로깅 도입     |
| Server/Client 경계 실수로 키 노출                    | 높음   | `'server-only'` 패키지 사용 + 코드 리뷰 + ESLint 룰 (후속)        |

### 모니터링 항목 (운영 시)

- 30초 타임아웃 발동률 → 동기 패턴 한계 신호
- mock fallback 발동률 → 별 의미 분류 (키 없음 / 실패 / 스키마)
- Route Handler별 평균 응답 시간
- `INTERNAL_ERROR` 발생 빈도
